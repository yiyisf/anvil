# 产品化升级清单

核心能力已跑通（两阶段流程、worktree 隔离、工单调度、流式、跨平台）。
这份清单梳理从「能用」到「团队能装能用能维护」还差什么。

条目编号用于讨论与排期引用。工作量是相对刻度（S ≈ 1 天内，M ≈ 2-4 天，L ≈ 1 周以上），
不是承诺。

---

## 0. 现状盘点

| 维度 | 现状 | 差距 |
|---|---|---|
| skill | 3 个内联字符串（implement / code-review / e2e），另有 2 段阶段 instructions | Matt 合集共 24 个，只覆盖了其中 4 个的语义，且是**手写重实现**而非加载 |
| skill 编排 | 每个工单固定跑三步，写死在 `SKILLS.map()` | 不能按需求类型选链路，不能插入 tdd / diagnosing-bugs |
| 安装 | git clone → npm install → 手写 `.env` → `npm run dev` | 没有一条命令的安装，宣导成本高 |
| 文档 | 单个 393 行 README，使用说明与踩坑记录混排 | 没有手册、没有配置参考、没有 skill 说明 |
| 错误提示 | `setErr(e.message)`，技术错误直接抛给用户 | `doctor.mjs` 已有分类诊断能力，前端完全没接 |
| 存储 | 本地文件 `.data/` | 单机单人，无法团队共享 |

### 一个已验证的技术前提

`@ai-sdk/harness` 的 `HarnessV1Skill` 支持 `files[]`（skill 相对路径 + 文本内容），
适配器会把它们materialize 到 `SKILL.md` 旁边。**加载真实 SKILL.md 目录在框架层是通的**，
不需要改框架，这是目标 1、2 能落地的基础。

### 一个已验证的坑

沙箱里 `$HOME` = `/`（实测），harness-pi 按 `$HOME/.agents/skills` 落 skill 文件，
即宿主的 `<WORKTREES_DIR>/.agents/skills/`。现在只有 3 个 skill 感觉不到，
装 24 个（每个含 SKILL.md + 引用文件）后会明显污染 worktree 父目录，且**每个会话重写一遍**。
见 S-05。

## 1. 补齐 skill 在研发流程中的使用场景

Matt 合集的 24 个 skill 与本工具流程的对应关系。「现状」列说明当前是怎么处理的。

### 1.1 分析阶段（需求对齐）

| skill | 用途 | 现状 |
|---|---|---|
| `grill-me` / `grilling` | 逐条追问直到边界清晰 | 手写 `ANALYST_INSTRUCTIONS` 实现了同类逻辑 |
| `grill-with-docs` | 追问 + 产出 `CONTEXT.md` 领域模型 | **完全没有**。本工具没有「项目上下文」这一层，每个需求都从零问起 |
| `research` | 带引用地调研外部事实/API | **完全没有**。需求涉及三方接口时只能靠模型记忆 |
| `domain-modeling` | 把零散条目升级成领域模型 | **完全没有**。`settled.fixed` 是平铺的 k-v，没有结构 |

### 1.2 移交阶段（规格与工单）

| skill | 用途 | 现状 |
|---|---|---|
| `to-spec` | 对话 → 规格 | 手写 `SPEC_INSTRUCTIONS` |
| `to-tickets` | 计划 → tracer-bullet 工单，带阻塞边 | 手写，但 `deps` 语义与 Matt 的阻塞边一致，可平滑替换 |
| `wayfinder` | 大工作量跨会话拆成调查工单 | **完全没有**。大需求一次性拆完，容易失控 |

### 1.3 实现阶段

| skill | 用途 | 现状 |
|---|---|---|
| `implement` | 按规格实现 | 手写内联版 |
| `code-review` | 按标准与规格并行审查 | 手写内联版 |
| `tdd` | 红-绿-重构循环 | 内联版里写了「最窄测试优先」一句话，没有循环约束 |
| `diagnosing-bugs` | 复现 → 最小化 → 假设 → 埋点 → 修 | **完全没有**。失败重试只是把失败原因塞回 prompt 重跑一次，没有方法论 |
| `prototype` | 一次性原型验证设计问题 | **完全没有** |
| `codebase-design` | 深模块 / 窄接口设计 | **完全没有**。工单涉及模块边界时无指引 |
| `resolving-merge-conflicts` | 按意图逐 hunk 解冲突 | **完全没有**。需求分支合回主干全靠人 |

> `e2e` 是本工具自有的 skill，Matt 合集里没有对应项，需要保留为本地 skill。
> 这决定了加载器必须支持**外部 skill + 本地 skill 合并**（见 S-02）。

### 1.4 平台自身与团队协作

| skill | 用途 | 现状 |
|---|---|---|
| `handoff` | 压缩会话供交接 | 有 jsonl 续接，但**无压缩**；长工单上下文会涨到不可控 |
| `improve-codebase-architecture` | 定期架构体检，出报告 | **完全没有**。可作为独立入口，不挂在需求下 |
| `triage` | 工单状态机流转 | 有自己的状态机，语义可对齐 |
| `writing-great-skills` | 团队写自己的 skill | **完全没有**。团队沉淀自有规范时需要 |
| `teach` | 多会话概念教学 | **完全没有**。与目标 3/4 的团队宣导直接相关 |
| `ask-matt` | 按情境路由到合适的 skill | 本工具是固定流水线，可作为「不知道该跑哪步」的入口 |

### 清单条目

| 编号 | 条目 | 说明 | 依赖 | 量 |
|---|---|---|---|---|
| **S-01** | skill 注册表 | 从磁盘扫描 SKILL.md 目录，解析 YAML frontmatter（name/description）+ 正文 + 同级引用文件 → `HarnessV1Skill` | — | M |

分四批，每批都能独立交付价值，不必等下一批。

**第一批 · 让 skill 真正可插拔**（S-01 S-02 S-03 S-05 I-01 I-02 I-03）

**第二批 · 让团队装得上**（P-01 P-02 P-03 P-04 D-01 D-03 D-05）

**第四批 · 让流程更强**（S-04 S-07 S-08 S-09 S-10 X-06 X-07 X-11 X-13 D-07）

## 7. 需要拍板的决策点

这几条会显著改变实现路径，先定了再动手更省事。

1. **skill 范围**：全量接入 24 个，还是先精选与主流程直接相关的一组？
2. **skill 来源与更新**：跟随上游自动更新，还是锁版本、人工评估后再升？
   skill 内容直接决定产出质量，自动更新意味着产出质量会无声漂移。
3. **分发形态**：公网 npm、内网 npm，还是 tar 包 / Docker？决定 P-01 与 I-06。
4. **产品定位**：个人本地工具，还是团队共享服务？决定 X-14，以及是否现在就要动存储层。
5. **e2e 的去留**：本工具自有的 `e2e` 与 Matt 的 `tdd` 职责有重叠，是保留双轨还是合并？
