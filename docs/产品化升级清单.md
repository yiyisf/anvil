# 产品化升级清单

核心能力已跑通（两阶段流程、worktree 隔离、工单调度、流式、跨平台）。
这份清单梳理从「能用」到「团队能装能用能维护」还差什么。

条目编号用于讨论与排期引用。工作量是相对刻度（S ≈ 1 天内，M ≈ 2-4 天，L ≈ 1 周以上），
不是承诺。

## 0. 现状盘点

| 维度 | 现状 | 差距 |
|---|---|---|
| skill | 3 个内联字符串（implement / code-review / e2e），另有 2 段阶段 instructions | Matt 合集共 24 个，只覆盖了其中 4 个的语义，且是**手写重实现**而非加载 |
| skill 编排 | 每个工单固定跑三步，写死在 `SKILLS.map()` | 不能按需求类型选链路，不能插入 tdd / diagnosing-bugs |
| 安装 | git clone → npm install → 手写 `.env` → `npm run dev` | 没有一条命令的安装，宣导成本高 |
| 文档 | 单个 393 行 README，使用说明与踩坑记录混排 | 没有手册、没有配置参考、没有 skill 说明 |
| 错误提示 | `setErr(e.message)`，技术错误直接抛给用户 | `doctor.mjs` 已有分类诊断能力，前端完全没接 |
| 存储 | 本地文件 `.data/` | 单机单人，无法团队共享 |

### 一个已验证的技术前提

`@ai-sdk/harness` 的 `HarnessV1Skill` 支持 `files[]`（skill 相对路径 + 文本内容），
适配器会把它们materialize 到 `SKILL.md` 旁边。**加载真实 SKILL.md 目录在框架层是通的**，
不需要改框架，这是目标 1、2 能落地的基础。

### 一个已验证的坑

沙箱里 `$HOME` = `/`（实测），harness-pi 按 `$HOME/.agents/skills` 落 skill 文件，
即宿主的 `<WORKTREES_DIR>/.agents/skills/`。现在只有 3 个 skill 感觉不到，
装 24 个（每个含 SKILL.md + 引用文件）后会明显污染 worktree 父目录，且**每个会话重写一遍**。
见 S-05。

## 1. 补齐 skill 在研发流程中的使用场景

Matt 合集的 24 个 skill 与本工具流程的对应关系。「现状」列说明当前是怎么处理的。

### 1.4 自研：端到端验证 skill

Matt 的合集覆盖了**单元层**的验证（`tdd` 红-绿-重构）与**代码层**的审查（`code-review`），
但没有任何 skill 回答「规格里写的场景，在跑起来的系统上是不是真的成立」。
这正是本工具的核心主张——`.agent/spec.feature` 是 Gherkin 场景，就该被逐条验证。

现在的 `e2e` 只是四行内联提示词，要升级成真正的 SKILL.md：

| 要解决的问题 | 现状 | 目标 |
|---|---|---|
| 场景到检查的映射 | 只说「逐条验证」，怎么验证靠模型自由发挥 | 明确：每个 `场景` 必须对应一个可执行检查，无法执行的要显式说明原因 |
| 项目类型识别 | 无 | 按栈识别测试命令（npm test / mvn test / pytest…），与 `sandboxTools` 白名单对齐 |
| 失败信息质量 | 「说明期望值与实际值的差异」 | 结构化：场景名、期望、实际、复现命令 |

| 环境不可用 | 与「测试不通过」混为一谈 | 区分「验不了」（缺命令、跑不起来）与「验了没过」，前者不该判 fail |

## 2. 初始化安装 Matt skills（全局一次性）

采用官方 CLI（`npx skills add`）而非自研拉取，装到 **pi 的全局 skill 目录**，
按默认版本、一次性安装。

### 2.1 已核实的三个事实

从 `skills@1.5.20` 的实际源码（`dist/cli.mjs`）确认，不是文档推断：

```js
pi: {
  skillsDir:       ".pi/skills",                  // 项目级
  globalSkillsDir: join(home, ".pi/agent/skills"), // 全局级 ← 我们要的
  detectInstalled: () => existsSync(join(home, ".pi/agent"))
}
```

1. **全局路径是 `~/.pi/agent/skills/<name>/SKILL.md`**，不是 `~/.agents/skills`。
   后者是 harness-pi 在**沙箱内部**落盘的位置，两者角色不同、不冲突。
2. **非交互标志齐全**：`--agent` `--skill` `--global` `--yes` `--all`，可完全脚本化，
   不必依赖交互式勾选。
3. **skill 内容从 `github.com` 拉取**（git clone 与 trees API），不走 npm；
   同时 CLI 支持本地路径作为源（源码里有 `isLocalPath` 分支）。

### 2.2 内网安装的真实约束

> ⚠️ **内网 npm 仓库只解决一半问题。**
> `npx skills` 这个 **CLI 包**可以从内网 npm 装；但它要装的 **skill 内容**走 `github.com`。
> 内网若不通 GitHub，`npx skills add mattpocock/skills` 仍然会失败。

两条可行路径，取其一：

- **A. 内网 git 镜像** —— 把 `mattpocock/skills` 镜像到内网 GitLab，
  `npx skills add <内网 git url> --agent pi --global`。CLI 支持任意 git URL，改动最小。
- **B. 随工具分发** —— 把 skill 目录随 anvil 包一起发到内网 npm，安装时用本地路径装。
  完全不依赖外网，但版本与上游解耦，需要人工同步。

建议 A，B 作为完全离线环境的兜底。

### 2.3 装完 ≠ 生效

> ⚠️ 这是最容易误判的一点。
> 本工具现在把 `server/skills.mjs` 里的**内联 JS 对象**交给 HarnessAgent，
> 完全不读磁盘。装到 `~/.pi/agent/skills/` 之后，**在加载器（S-01）做出来之前，
> 本工具一个都用不上**。安装与生效是两件事，排期上必须绑在一起。

### 2.4 清单条目

| 编号 | 条目 | 说明 | 依赖 | 量 |
|---|---|---|---|---|

| **I-02** | 一次性安装命令 | `anvil skills install` 封装 `npx skills add <源> --agent pi --global --yes --skill <清单>` | I-01 | M |
